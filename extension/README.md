# StartPress 확장 프로그램 프론트

고객사·메인 사이트·IndexNow 설정·새 글 저장 및 알림을 기존 FastAPI에 연결한 프론트입니다.
로컬 웹과 Chrome에 설치하는 Manifest V3 패키지로 실행할 수 있습니다.

## Chrome에 로드

```bash
cd extension
npm ci
npm run build
```

1. Chrome에서 `chrome://extensions`를 열고 개발자 모드를 켭니다.
2. **압축해제된 확장 프로그램 로드**에서 프로젝트의 `extension/dist` 폴더를 선택합니다.
3. 도구 모음의 StartPress 아이콘을 누르면 관리 화면이 새 탭으로 열립니다.

원본 설정은 `public/manifest.json`, Chrome이 읽는 빌드 결과는 `dist/manifest.json`입니다.
`src/background.ts`는 `dist/background.js`로 빌드되며 아이콘 클릭만 처리합니다.
코드를 변경하면 다시 빌드하고 확장 프로그램을 새로고침한 뒤 관리 탭도 다시 여세요.

설치된 확장 프로그램은 `http://127.0.0.1:8000`의 FastAPI로 직접 연결하므로 아래 개발 서버가 실행 중이어야 합니다.
웹 개발 서버의 `/api` 프록시는 기존대로 유지합니다. `.env`나 인증 파일을 확장 프로그램에 복사하지 않습니다.
현재 호스트 권한은 로컬 API용 `http://127.0.0.1/*`만 선언하며 Chrome 호스트 권한은 포트별로 제한되지 않습니다.
팀 배포 시 API 주소와 허용 호스트를 운영 HTTPS 서버에 맞게 변경해야 합니다.

네이버·Bing은 로그인된 작업 탭 선택과 사이트·URL별 GUI 자동 조회를 지원합니다. GUI 관측의 DB 저장은 후속 작업입니다.
예시 화면만 보려면 열린 관리 화면의 URL에 `?mode=demo`를 붙이세요.

## 실행

프로젝트 루트에서 기존 `startpress` 환경과 PostgreSQL을 사용해 서버를 실행합니다.
개발 DB 설정은 기존 환경을 따르며 `.env`를 프론트로 복사하지 않습니다.

```bash
conda activate startpress
PYTHONNOUSERSITE=1 python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

다른 터미널에서 프론트를 실행합니다.

```bash
cd extension
npm ci
npm run dev
```

- `http://127.0.0.1:5173/`: 실제 API 모드. 저장 버튼은 DB에 반영되며 알림을 선택하면 실제 IndexNow 요청이 발생합니다.
- `http://127.0.0.1:5173/?mode=demo`: 예시 모드. 서버 호출·DB 저장·외부 전송 없이 동작합니다.

Vite 개발 서버가 `/api` 요청을 `127.0.0.1:8000`의 기존 경로로 전달합니다.
서버 연결 실패 시 오류와 목록 재조회 버튼을 표시하며 예시 데이터로 자동 대체하지 않습니다.
빌드 결과를 별도 호스팅할 때는 `/api`를 FastAPI로 전달하는 역방향 프록시 설정이 필요합니다.
팀 배포 전 팀원 인증·HTTPS를 추가해야 합니다.

## 연결 범위

첫 화면은 **고객사 대시보드**입니다. 왼쪽 위에서 고객사를 선택하고, 발행 알림·색인 상태 화면의
블로그 선택에서 해당 고객사 소속 사이트를 고릅니다. 고객사 관리는 전체 고객사를 대상으로 합니다.
대시보드에는 등록 블로그·글 수, Google·Bing별 저장 상태, 최근 오류 건수와 블로그별 현황을 표시합니다.
통계는 DB에 등록된 글만 대상으로 하며 메인페이지를 제외하고 비활성 항목은 포함합니다.
고객사를 전환하면 글 초안·선택 블로그를 분리하고 이전 고객사의 늦은 통계 응답은 무시합니다.
상세 집계 기준은 [대시보드 API](../docs/dashboard-api.md)를 참고하세요.

| 기능 | API |
|---|---|
| 고객사별 대시보드 통계 | GET `/clients/{id}/dashboard` |
| 고객사 등록·목록 | POST·GET `/clients` |
| 사이트 정보 등록·고객사별 목록 | POST·GET `/sites` |
| IndexNow 설정 조회·교체 | GET·PUT `/sites/{id}/indexnow-settings` |
| 글 저장·선택적 IndexNow 알림 / 저장된 글 목록 | POST·GET `/sites/{id}/pages` |
| 저장된 검사 결과 / 새 Google·Bing 조회 | GET·POST `/sites/{id}/inspections` |

- 사이트 정보 저장은 실제 검색엔진 등록·소유 확인과 구분합니다.
- 목록은 limit·offset 페이지를 끝까지 조회하고 서버 UUID를 사용합니다.
- IndexNow 설정 조회는 `configured`, `key_location`만 사용합니다. 키 원문은 설정 제출 때만 입력하며 화면 모델·로컬 저장소에 보관하지 않습니다.
- 설정이 없거나 불일치하면 직접 알림을 막지만 알림 체크를 해제해 글만 저장할 수 있습니다.
- 글 제목과 URL을 같은 순서로 한 줄씩 입력합니다. 여러 글은 순차 요청하며 글별 DB 저장·알림 결과를 별도로 표시합니다.
- HTTP 201도 알림 성공을 뜻하지 않습니다. `accepted`, `key_pending`, `failed`, `unknown`, `skipped`를 따로 표시합니다.
- 결과 불명·서버 오류 시 남은 전송을 중단합니다. 쓰기 요청은 자동 재시도하지 않습니다.
- 이미 저장했거나 저장 여부가 불명확한 글은 같은 화면 세션에서 다시 보내지 않습니다.
- 글 목록은 GET으로 다시 읽을 수 있지만 알림 재시도 API·서버 제출 이력은 아직 없습니다. 이번 알림 결과와 이력은 메모리에만 유지되므로 새로고침하면 사라집니다.
- 고객사 요청·블로그 링크 경로는 문구·메모만 준비하며 글 DB 저장·외부 메시지 전달·실제 블로그 발행을 수행하지 않습니다.
- 색인 상태 화면에서 메인페이지·글을 선택하면 GET으로 저장된 엔진별 요약 상태를 읽습니다. 페이지 진입·엔진 선택만으로 외부 조회를 실행하지 않습니다.
- 대시보드·색인 상태 화면의 **고객사 전체 색인 조회** 버튼은 선택 고객사의 모든 활성 메인 사이트와 등록된 활성 글을 대상으로 합니다. 블로그·URL·엔진 선택은 저장 결과 필터이며 실행 범위를 제한하지 않습니다.
- 기존 목록 API의 모든 페이지를 읽어 실행 대상을 확정한 뒤 Google·Bing 단일 URL 검사 API를 순차 호출합니다. 목록 수집에 실패하면 일부 대상만 검사하지 않고 시작을 중단합니다. 네이버는 서버 검사 API로 보내지 않습니다.
- Google은 색인 관측을 저장하고, Bing은 크롤링 관측만 저장합니다. 네이버·Bing은 GUI에서 새 응답을 확인해 이번 작업 표에 보관합니다. GUI 관측의 DB 저장은 아직 지원하지 않습니다. 사이트맵·IndexNow·색인 생성 요청은 전체 조회에 포함하지 않습니다.
- 개별 URL 오류는 기록하고 계속합니다. 인증·한도 오류는 해당 엔진의 남은 API 작업을 중단하고, 서버 연결·응답이 불명확하면 전체 남은 API 작업을 중단합니다. 자동 재시도하지 않습니다.
- 실행은 시작 당시 고객사에 고정됩니다. 중복 실행을 막고 고객사를 바꿔도 이전 실행의 URL별 결과를 섞지 않습니다. 취소하면 진행 중 요청은 결과를 확인하고 다음 요청부터 중단합니다. 기존 성공 관측은 오류로 덮어쓰지 않습니다.
- 처리 현황·이번 실행 목록은 관리 탭의 메모리에만 유지됩니다. 관리 탭 닫힘·새로고침 시 자동 재개하지 않습니다. Google·Bing API 관측은 서버에 저장되며 GET으로 다시 확인할 수 있습니다. 네이버·Bing GUI 관측은 이번 실행 화면의 메모리에만 보관합니다.
- 전체 실행은 `src/inspection/client-plan.ts`, `src/inspection/client-controller.ts`, `src/inspection/client-view.ts`로 분리했습니다. 대상 확정 후 `start()`에서 네이버·Bing의 `src/tabs/controller.ts`를 엔진별로 호출해 탭부터 준비합니다.
- 탭이 하나면 자동 선택 후 주소·문서 준비 상태를 재검증하고, 여러 개면 엔진별 선택 폼에서 사용자 선택을 기다립니다. 탭이 없거나 웹 개발 환경이면 준비 안내와 목록 재조회, **탭 준비를 건너뛰고 API 조회만 계속**을 제공합니다. 준비되지 않은 상태에서 API를 자동 실행하지 않습니다.
- 선택한 탭은 현재 전체 실행에 저장하므로 블로그·URL·화면의 엔진 필터를 바꿔도 유지됩니다. 새 전체 실행은 새 실행 ID로 다시 준비하고 이전 실행의 선택 폼은 무시합니다. 선택 대기 중 취소도 지원합니다.
- 탭이 모두 준비되거나 사용자가 API 전용 진행을 선택하면 기존 API 순차 실행을 이어갑니다. 탭 준비는 로그인·사이트 접근 권한 확인 또는 GUI 조회·저장 성공을 의미하지 않습니다. 네이버·Bing 탭이 준비되면 API 처리 후 사이트별 GUI 자동 조회를 실행합니다. API 전용 진행을 선택하면 GUI 작업은 미실행으로 남습니다.
- API가 제공하지 않는 크롤링 시각·제출 이력을 생성하지 않습니다. Bing의 crawled를 indexed로 바꾸거나 unknown을 미색인으로 바꾸지 않습니다.
- 예시 모드는 여전히 외부 요청 없이 가짜 관측값으로 동작합니다.

## 검증

Node.js 24 환경에서 확인했습니다.

```bash
npm test
npm run build
```

테스트는 주입한 가짜 HTTP 응답으로 요청 필드·페이지네이션·오류 메시지·순차 실행·중단 정책을 검증합니다.
jsdom으로 실제 화면 코드를 실행해 고객사 전환·블로그 이동·초안 분리·응답 순서도 확인하며 실제 DB나 검색엔진을 호출하지 않습니다.

## 오류 화면

- 공통 오류 모델은 HTTP 상태·코드·입력 위치·작업 종류를 보존하고 원문 입력·예외 문맥은 버립니다.
- 오류 카드에는 실패한 작업, 확인된 원인, 다음 행동을 표시합니다. 오류 정보는 펼쳐서 확인할 수 있습니다.
- 입력 오류는 해당 필드의 설명과 `aria-invalid`에 연결하고, 입력을 유지한 채 첫 오류로 포커스를 이동합니다.
- 화면을 다시 그려도 같은 사이트·화면의 작성 중인 값은 유지합니다. 키·키 파일 주소는 별도 초안이나 로컬 저장소에 직렬화하지 않으며, 같은 화면의 입력 DOM만 잠시 재사용하고 저장 성공 시 초기화합니다.
- Google 인증 오류는 API 연결 안내만 제공하며, 아직 없는 로그인·재연결 기능을 버튼으로 위장하지 않습니다.
- 검사 실패는 이전 성공 상태와 성공 시각을 유지하며 미확인·미색인으로 바꾸지 않습니다. 같은 오류를 중복 표시하지 않습니다.
- 글 처리의 일부 실패·대기·결과 불명은 경고로 안내합니다. 결과 불명인 글은 GET으로 저장 여부만 확인할 수 있으며, 목록에서 발견되지 않아도 미저장을 단정하지 않습니다.
- 복구 버튼은 목록·저장 결과를 읽습니다. 글 저장·알림 전송·새 색인 검사를 자동 재실행하지 않습니다.
- `http://127.0.0.1:5173/?mode=demo&error=auth`에서 외부 요청 없는 인증 오류 화면 예시를 볼 수 있습니다.
- 백엔드 오류 코드 저장에는 Alembic 0003이 필요합니다. 기존 오류의 세부 원인은 소급 추정하지 않습니다.

## 후속 방향

공식 API 색인 조회의 수동 실행은 연결했으며, 중앙 서버의 주기적 실행은 후속 작업입니다.
네이버 GUI 조회는 사용자가 로그인된 작업 탭을 준비하고 확장 프로그램에서 수동 실행하는 방향입니다.
네이버 인증 만료·추가 인증 시 중단하며 두 경로의 관측 결과와 마지막 확인 시각을 엔진별로 저장합니다.

## 네이버 기존 결과 읽기

- 실제 확인한 경로는 **검증 → 색인 상태 확인**인 `/console/site/check/inspection`입니다. 비슷한 이름의 URL 검사·간단체크·요약 화면은 지원하지 않습니다.
- 전체 실행에서 네이버 탭을 준비한 뒤 **작업 탭 → 현재 네이버 결과 읽기**로 현재 표시된 결과만 가져옵니다. 끝난 실행은 작업 탭 영역을 펼치세요.
- 현재 확인한 성공·검사 결과 없음 문구와 사이트·입력창 URL·엔진 표시 업데이트·화면을 읽은 시각을 표시합니다. 아이콘 텍스트는 판독에서 제외합니다. 확인하지 않은 다른 문구는 추정하지 않습니다.
- 기존 결과와 현재 입력 URL의 연결·최신 조회 여부는 입증되지 않았으므로 관측 미리보기로만 제공합니다. DB 저장·최신 색인 상태 변경·전체 완료 수 갱신은 하지 않습니다.
- 같은 확장의 관리 페이지 요청만 받고 프레임 0에서 읽습니다. 기존 결과 읽기 버튼은 페이지를 조작하지 않습니다. 별도의 전체 자동 조회는 아래 고정 동작만 수행하며 로그인 폼·쿠키·토큰·페이지 원문은 수집하지 않습니다.
- 네이버는 인증 콜백에서 콘솔로 SPA 이동할 수 있어 Content Script 수신기는 `searchadvisor.naver.com/*`에 등록합니다. 판정은 검사 경로에서만 읽고 사이트 목록에서는 해당 메인 사이트 링크만 선택합니다. 인증·로그인 화면에서는 DOM을 읽지 않습니다. 기존 호스트 권한은 늘리지 않습니다.
- 빌드는 관리 화면과 별도로 Content Script를 import 없는 IIFE인 `dist/naver-content.js`로 생성합니다. 설치 후에는 **확장 새로고침 → 네이버 탭 새로고침 → 네이버에서 URL 재조회 → 관리 탭 다시 열기**가 필요합니다.

## 프론트 코드 구조

```text
src/
├─ main.ts                       # 화면과 이벤트 연결

   └─ naver/
```

공통 탭 모듈은 네이버의 판정 문구나 DOM 구조를 알지 않습니다. 네이버 읽기·미리보기 구현은 `engines/naver/`에 모으고 전체 실행 모듈에서 호출합니다. Content Script의 소스 진입점은 `src/engines/naver/content.ts`이며 배포 파일명은 기존 `dist/naver-content.js`를 유지합니다.

## 네이버 사이트·URL별 자동 조회

- **고객사 전체 색인 조회**에서 준비된 네이버 탭을 사용합니다. 현재 활성 대상에는 메인페이지와 등록된 활성 글이 포함됩니다.
- 사이트별 흐름: `/console/board` 이동·준비 확인 → URL이 일치하는 메인 사이트 링크 클릭 → 선택된 사이트 확인 → 색인 상태 확인 화면 이동 → URL 입력·확인 → 새 응답 판독 → 나머지 URL 반복 → 사이트 목록 복귀 → 다음 사이트.
- `engines/naver/observation.ts`에 화면 판독·사이트 선택·URL 입력·확인과 통신 타입·오류를 모았습니다. `automation.ts`는 탭 이동·순서를 관리하고 `content.ts`는 고정 명령 수신과 작업·문서 ID 검증을 담당합니다.
- 확인 버튼은 표시된 이름이 정확히 **확인**인 경우 하나만 선택합니다. **수집 요청·사이트 등록·삭제** 버튼은 호출하지 않습니다.
- 입력 이벤트를 발생시키고 이전 결과 노드의 제거·교체·문구 변화가 확인되어야 새 관측으로 인정합니다. 이전 결과가 그대로면 시간 초과로 중단하며 자동 재조회하지 않습니다.
- 실제 확인한 성공 문구는 `indexed`, **URL 검사 결과가 없습니다.**는 `unknown`으로 처리합니다. 결과 없음은 미색인 확정이 아닙니다. 다른 문구는 추정하지 않습니다.
- 인증 필요·권한 없음·사이트 미발견·문서/URL 변경·사용자 개입·시간 초과·취소 시 네이버 순회를 중단합니다. 취소는 현재 DOM 작업에 전달하고 이후 URL·사이트 이동을 시작하지 않습니다.
- 결과는 작업 표의 **GUI 관측 · DB 미저장**과 네이버 GUI 처리 건수로 표시합니다. API 저장 건수와 분리합니다. 네이버 결과 저장 API는 아직 추가하지 않았습니다.
- 전체 순회의 실제 Chrome 검증은 도구 시간 초과로 미완료입니다. 가짜 DOM·두 사이트 순회·취소·전체 화면 연결 테스트와 빌드는 통과했습니다.

- 결과 제목의 아이콘·SVG·장식 텍스트를 제거한 뒤 판정 문구만 비교합니다. 아이콘만 바뀐 것은 새 응답으로 인정하지 않습니다. **URL 검사 결과가 없습니다.**는 화면에 **수집 확인 안 됨**으로 표시하고 내부 상태는 `unknown`을 유지합니다. 네이버가 수집 데이터 없음 또는 URL 이상 가능성을 함께 안내하므로 실제 미수집으로 확정하지 않습니다.


## Bing 사이트·URL별 자동 조회

- **고객사 전체 색인 조회**에서 선택한 Bing 탭 하나를 사용합니다. 처음에 URL 검사 화면으로 이동한 뒤 **왼쪽 위 사이트 선택 → 메인 URL과 등록 글을 하나씩 검사 → 다음 사이트 선택** 순서로 진행합니다.
- `src/engines/bing/content.ts`는 관리 페이지의 고정 명령만 받고, `observation.ts`는 사이트 선택·입력·판독, `automation.ts`는 사이트별 순서와 취소·응답 검증을 담당합니다.
- 실제 화면에서 확인한 `data-tag="urlInspectionInput"`, `inspectBtn`, `BingdexTab`, `urlInspectionIndexCard`를 사용합니다. 사이트 항목은 표시 이름 대신 링크의 `siteUrl` 값으로 비교합니다. 목록에 정확한 사이트가 없거나 여러 개면 중단합니다.
- 검사 중 표시 또는 결과 카드 교체·변경 이후, 선택 사이트·입력 URL·결과 주소의 `urlToInspect`가 모두 맞고 **Bing 색인** 탭이 활성화된 경우에만 결과를 인정합니다. 같은 URL 재조회는 로딩 후 완료를 확인합니다. 라이브 URL과 색인화 요청은 실행하지 않습니다.
- 명시적 색인 성공은 `indexed`, 명시적 미색인 문구는 `not_indexed`, 나머지는 `unknown`으로 보관합니다. 제외 사유·대표 URL·페이지 가져오기 성공·표시된 마지막 크롤링 시각도 읽습니다. 대표 URL은 자동으로 재검사하지 않습니다.
- 기존 Bing API 크롤링 저장과 GUI 색인 관측은 **Bing API / Bing GUI** 두 행으로 구분합니다. GUI 결과는 이번 실행 화면에만 보관하며 API 저장 건수나 서버 상태를 덮어쓰지 않습니다.
- 빌드는 `dist/bing-content.js`를 import 없는 IIFE로 생성합니다. `npm run build` 후 **확장 새로고침 → Bing 탭 새로고침 → 관리 탭 다시 열기**를 진행합니다.
- 실제 계정에서 사이트 메뉴와 메인·글 URL의 검사 결과 구조를 확인했습니다. 새 콘텐츠 스크립트의 실제 Chrome 전체 순회는 아직 미검증이며, 여러 사이트 순회·DOM 판독·취소·응답 불일치·전체 조회 연결은 모의 테스트로 검증합니다. 실행 기록은 Git 제외된 `.secrets/bot_runs/`에 보존합니다.


### Bing 사이트 전환과 오류 단계

- 왼쪽 메뉴의 사이트 항목에서 실제 `href`를 읽고 같은 Bing 출처·URL 검사 경로·정확한 `siteUrl`인지 재검증한 뒤 선택한 탭을 이동합니다. 합성 링크 클릭만으로 전환 성공을 가정하지 않습니다.
- 메뉴와 항목이 나뉘어 렌더될 수 있어 항목을 최대 15초 기다립니다. 전환 후에는 새 문서의 선택 사이트와 검사 입력칸 준비를 확인합니다.
- 진행 안내와 시간 초과 메시지는 URL 검사 화면 준비, 사이트 목록 확인, 사이트 전환, URL 입력 준비, 검사 결과, 검사 후 확인 단계를 구분합니다. 네이버 실행 시간은 Bing의 단계별 제한 시간에 포함하지 않습니다.

- 실제 Bing의 Fluent UI는 `ms-Layer` 부모에 `visibility:hidden`, `ms-Layer-content` 자식에 `visibility:visible`을 사용합니다. 보임 여부는 대상 요소의 최종 visibility로 판단하고, 부모 체인은 display:none만 확인합니다. 부모 visibility만으로 메뉴를 숨김 처리하던 오류를 실제 화면 대조로 수정했습니다.

- 수정 후 사용자가 확장을 다시 로드해 조회를 시작했으며, 실제 Bing 탭에서 사이트 선택을 통과하고 등록 글 URL의 색인 결과 카드에 도달한 것을 확인했습니다. 여러 실제 사이트 간 전환과 관리 화면의 최종 관측 건수는 별도 미검증입니다.


## 네이버·Bing GUI 병렬 실행

- API 조회가 끝나면 네이버와 Bing GUI를 서로 다른 작업 탭에서 동시에 시작합니다. 네이버 완료를 기다린 뒤 Bing을 시작하지 않습니다.
- 각 엔진 안에서는 사이트별 URL을 하나씩 검사합니다. 엔진별 제한 시간과 오류 처리는 독립적이며 한쪽의 로그인 만료·실패가 다른 쪽의 조회를 중단하지 않습니다.
- 전체 실행은 두 GUI가 모두 끝난 뒤 완료 처리합니다. 실행 취소는 양쪽에 전달하고 완료된 API 저장·GUI 관측은 유지합니다.
- 전체 진행 안내는 병렬 실행 중임을 표시하고 사이트·URL별 세부 단계는 결과 표의 각 엔진 행에 표시합니다.
