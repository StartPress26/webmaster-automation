# 고객사 대시보드

`GET /clients/{client_id}/dashboard`는 선택 고객사의 블로그별 등록 글과 저장된 엔진 상태를 집계한다.
미존재 고객사는 404, UUID 형식 오류는 422다. 블로그가 없는 고객사는 빈 통계를 200으로 반환한다.

## 응답

- `client`: 고객사 ID·이름·담당자·생성 시각.
- `site_count`: 고객사 소속 메인 사이트 수.
- `page_count`: 해당 메인 사이트에 속하고 고객사 ID가 일치하는 등록 글 수.
- `google`, `naver`, `bing`: 고객사 전체 등록 글의 엔진별 상태 합계.
- `sites`: 블로그 ID·이름·URL·활성 여부·등록 글 수·엔진별 상태. 생성 시각·ID 오름차순이다.

엔진별 필드는 다음과 같다.

| 필드 | 의미 |
|---|---|
| `indexed` | 저장된 색인 확인 |
| `not_indexed` | 저장된 미색인 확인 |
| `crawled` | 크롤링 확인, 색인 여부 미확인 |
| `submitted` | 알림 접수 후 수집·색인 여부 미확인 |
| `failed` | 성공 관측 시각이 있는 기존 처리 오류 상태 |
| `unknown` | 미확인 상태 또는 성공 관측이 없는 글 |
| `error_count` | 최근 오류가 저장된 글 수. 위 상태 건수와 겹칠 수 있음 |
| `last_checked_at` | 등록 글 중 가장 최근 성공 관측 시각. 없으면 null |

## 집계 기준

- 메인페이지 자체의 검사 결과는 글 통계에서 제외한다. 비활성 블로그·글은 포함한다.
- 아직 DB에 등록하지 않은 실제 블로그 글은 집계하지 않는다.
- 상태 행이 없거나 `last_checked_at`이 null이면 미확인으로 집계한다. 미색인으로 추정하지 않는다.
- 재검사 오류가 있어도 이전 성공 상태는 통계에 유지하고 오류 건수를 별도로 표시한다.
- 엔진 하나의 상태 6개 합은 `page_count`와 같다. Google·네이버·Bing의 건수는 서로 합산하지 않는다.
- Bing `crawled`를 `indexed`로 변환하지 않는다. 네이버는 GUI에서 저장한 최신 요약 상태를 집계하며 결과 없음·미검사 글은 미확인으로 유지한다.
- GET은 DB 조회만 하며 신규 검사·외부 제출·상태 변경을 실행하지 않는다.
- 기존 테이블을 사용하고 새 마이그레이션은 없다. 집계 쿼리는 `error_code` 컬럼을 읽지 않는다.

## 화면 연결

- 첫 진입은 대시보드다. 왼쪽 위에서 고객사를 선택한다.
- 발행 알림·색인 상태 화면에서는 해당 고객사 소속 블로그를 별도로 선택한다.
- 사이트 등록은 선택 고객사 ID를 사용한다. 고객사 관리는 전체 고객사를 관리한다.
- 고객사 변경 시 이전 고객사의 통계 응답은 버린다. 글 입력 초안은 고객사·사이트·화면별로 분리한다.
- 대시보드 진입·고객사 변경·통계 새로고침 시 저장된 통계를 읽는다.
- 네이버도 전체 색인 확인 카드·엔진별 상태·블로그별 색인 확인 건수와 최근 성공 관측 시각을 표시한다.
- 네이버 필드가 추가된 서버를 먼저 배포한 뒤 새 확장 빌드를 적용한다.

## 검증

`tests/integration/test_dashboard_api.py`는 임시 PostgreSQL에서 고객사 분리, 빈 목록,
미검사 글, 비활성 항목, 이전 성공 상태 보존, 읽기 전용 조회를 검증한다.
`extension/tests/dashboard.test.mjs`와 `workspace.test.mjs`는 API 요청과 DOM에서 고객사 전환,
블로그 이동, 초안 분리, 늦은 응답 무시를 검증한다. 실제 검색엔진 호출은 하지 않는다.
